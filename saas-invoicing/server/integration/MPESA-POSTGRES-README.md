# M-Pesa and receipt PostgreSQL integration tests

This opt-in suite uses real PostgreSQL connections, transactions, locks, migrations, indexes, triggers, and the `pg` driver. The ordinary `npm test` suite does not load it. The test double is injected into the initiation service; the harness never imports Daraja client code or sends provider requests.

## Existing harness audit

`accounting-postgres.js` is opt-in and uses `ACCOUNTING_TEST_DATABASE_URL` plus an explicit confirmation without falling back to `DATABASE_URL`. It checks the actual database name against the `invoxa_accounting_test_` prefix, connected role against the URL username, database marker, writable/non-recovery state, non-superuser status, `uuid_generate_v4()`, public-schema privileges, and an empty user-relation catalog. It serializes its invocations with an advisory lock, applies the accounting foundation and configuration migrations, and removes an allowlist of objects. Its code accepts any hostname in a well-formed URL, and its baseline creates only `tenants`; it has no clients, invoices, payments, receipts, reservations, or reconciliation tables.

`invoice-accounting-postgres.js` requires its fixed `127.0.0.1:5432` database and role, accounting marker, writable non-superuser target, `uuid-ossp`, public-schema privileges, and an empty user-relation catalog. Its launcher clears ambient application/libpq database variables. It applies a synthetic invoice fixture and accounting/invoice migrations, uses independent pool connections for concurrent route requests, and cleans its known fixture objects. It does not install customer receipt or M-Pesa migrations. Neither existing suite is a substitute for this M-Pesa harness or evidence of production core-table DDL.

Reusable patterns are dedicated opt-in variables and confirmation, catalog identity checks, a database comment marker, a suite advisory lock, an explicit migration list, independent pool connections, rollback on failure, and allowlisted cleanup. This harness adds a fixed loopback endpoint and exact database/role allowlist, stricter schema emptiness checks, and the synthetic `payments` baseline needed by the M-Pesa migrations.

## Fixed safety contract

The harness accepts only the exact local target `127.0.0.1:5432/invoxa_mpesa_test_local` and role `invoxa_mpesa_test_role`. It requires `MPESA_TEST_DATABASE_URL` and confirmation `MPESA_TEST_DATABASE_CONFIRMATION=I_CONFIRM_THIS_IS_A_DISPOSABLE_MPESA_TEST_DATABASE`. It has no `DATABASE_URL`, `.env`, dotenv, or application database configuration fallback. Any ambient `DATABASE_URL` or `PG*` connection setting causes an early refusal. The URL query string is rejected.

Before creating fixtures or applying migrations, it checks the URL statically, then runs read-only catalog checks for PostgreSQL 10 or newer, the exact database, connected role, server-reported loopback address and port, comment `INVOXA_DISPOSABLE_MPESA_TEST`, a writable non-recovery database, and a non-superuser role that is not database/public-schema/extension/UUID-function owner and has no memberships, elevated role attributes, database `CREATE` or `TEMP` privilege. The role needs only database `CONNECT`, `USAGE`/`CREATE` on `public`, and execute permission on the preinstalled `uuid_generate_v4()`. This means the disposable database must revoke the default `TEMPORARY` grant (often granted to `PUBLIC`) before the test role is used. It verifies `uuid-ossp` and the PL/pgSQL language (required by the trigger migrations), allows only `uuid-ossp` and PostgreSQL's optional `plpgsql` extension, takes a suite advisory lock, and checks `public` for relations, routines and standalone user types, plus database event triggers and additional user schemas. The advisory lock only coordinates this harness; keep the disposable database exclusive while it runs. The server-reported endpoint check rejects common remote forwarding configurations, but is not cryptographic proof of server provenance: the approved target must be a directly connected, locally administered disposable PostgreSQL instance, with no tunnel or proxy.

The harness does not create databases, roles, extensions or database markers. Provision and approve this exact disposable local target separately. The role needs `CONNECT`, `USAGE`/`CREATE` in `public`, and UUID function execution; it must not own the database, schema, extension, or UUID function and must not have `TEMP`, elevated role attributes, or role memberships. Objects it creates are owned by that role. Each fixture/migration object is tagged with a fresh per-run SQL comment inside the fixture or migration transaction. Cleanup checks both the explicit object allowlist and that run marker before dropping a table or function; if an unmarked object with an expected name remains, cleanup rolls back and leaves the target untouched for reprovisioning. It never drops the database or extension. Do not run unrelated DDL in the target during the suite. If setup marking or cleanup fails, discard and reprovision the disposable database before another run. Never point the URL at Neon or another remote host.

Run from `server` after the target is provisioned:

```powershell
integration\run-mpesa-postgres.cmd
```

The launcher prompts for the local test-role password with hidden input, constructs the fixed loopback URL in its process, clears ambient application/libpq database variables for the child process, and removes the dedicated test variables afterward. It does not provision the target. The npm script can also be invoked directly after setting the two dedicated variables in a controlled local process.

## Synthetic schema and migration assumptions

The suite reuses `invoice-fixture-schema.sql`, which labels the core tenant, user, client and invoice schema as a minimal test fixture. `mpesa-payments-fixture.sql` is a synthetic `payments` stub. It includes UUID `id`, UUID `tenant_id`, UUID `invoice_id`, numeric `amount`, and `phone_number`, `mpesa_checkout_id` and `status` columns needed by the reviewed migration checks and service queries. Production legacy DDL is absent from the repository; passing this suite says nothing about production-schema compatibility.

The harness applies these migrations once, in order, to its verified empty database:

1. `20261021_001_accounting_foundation.sql` requires `tenants.id` UUID with a unique key and `uuid_generate_v4()`.
2. `20261022_001_invoice_accounting_configuration.sql` depends on the accounting foundation and tenant-scoped account/journal keys.
3. `20261023_001_customer_receipts.sql` requires UUID tenant/client/invoice IDs, non-null `invoices.total` numeric scale 2, text-compatible invoice status/number, date `due_date`, accounting settings/period/accounts/mappings/tax snapshots/journals, and scoped unique keys. It adds receipt/allocation tables, foreign keys, balance triggers and audit triggers.
4. `20261030_002_accounting_period_close_audit.sql` requires tenant-scoped accounting periods and is included for the accounting/receipt context.
5. `20261030_003_mpesa_reconciliation_audit.sql` requires the legacy payment columns plus `customer_receipts(tenant_id,id)`. It adds tenant/idempotency uniqueness, one provider-success row per tenant/checkout, a receipt-scope FK and an immutable audit trigger.
6. `20261031_002_mpesa_stk_initiation_idempotency.sql` requires unique UUID `tenants.id`, UUID `payments.tenant_id`, numeric `payments.amount`, the legacy payment columns, and `uuid_generate_v4()`.
7. `20261031_003_mpesa_stk_invoice_reservations.sql` requires the exact request/event checks and types created by 002. It adds `details`, terminal statuses and partial unique indexes.

For `payments`, the reconciliation migration requires columns `id`, `tenant_id`, `invoice_id`, `amount`, `mpesa_checkout_id` and `status`; 002 also requires `phone_number`. Migration 002 validates UUID `tenants.id` with a valid single-column unique key, UUID `payments.tenant_id`, and numeric-category `payments.amount`. It checks the remaining payment columns for presence, not their types. The fixture chooses UUID payment/invoice IDs and varchar text fields solely to satisfy the reviewed test SQL. No FK from an STK request to legacy invoices or payments is added because production identifier types/keys are undocumented.

`20261030_003_mpesa_reconciliation_audit.sql` does not set a local `search_path` while using the unqualified `uuid_generate_v4()` default. The harness pins `search_path=public,pg_catalog`; a deployment migration runner must likewise resolve the preinstalled function in `public` or the migration will fail. Production compatibility requires the authoritative core-table DDL and the deployed migration ledger: verify exact payment identifier types and keys, actual tenant relationships, the state/data population, and whether any of these objects were already partially applied. The harness's empty synthetic schema does not validate populated-schema locking duration or duplicate cleanup.

`mpesa_stk_one_active_request_per_invoice_uq` reserves `(tenant_id, invoice_id)` for `reserved`, `outcome_unknown`, `provider_accepted`, `reference_recovered`, `payment_recorded` and `provider_succeeded`. `provider_rejected` and `resolved_no_collection` are terminal and release that index entry. The payment index allows only one non-null `(tenant_id, payment_id)`. The suite checks each active state against the actual partial unique index and checks terminal release.

These M-Pesa migrations cannot run alone on an empty schema: tenant/client/invoice/payment baselines, `uuid-ossp`, accounting foundation/configuration and customer receipts must exist first. Migration 002 is transactional and refuses existing initiation tables; it does not inspect historical payment rows for matches. Migration 003 checks active duplicates, payment links, unexpected statuses, details/checks and index names before creating its indexes. The DDL is transactional; a concurrent duplicate appearing after its duplicate preflight still causes unique-index creation to fail and rolls back the migration. Reconciliation audit creation is unconditional and is not rerunnable. Customer receipt and accounting migrations have unconditional object creation; the receipt migration's `IF NOT EXISTS` scoped indexes do not make its whole migration idempotent. The harness applies no migration twice.

On populated production schemas, authoritative DDL and data checks remain mandatory. In particular, verify the real `payments` types/keys, tenant ownership and invoice key relationship, existing duplicate allocations/receipts, all live STK request states/payment links, and migration history before deployment. The harness uses a fresh synthetic fixture and cannot establish any of these production facts. `uuid-ossp` is a prerequisite installed outside the migrations; the harness never creates it.

Each SQL migration owns its transaction. Fixture DDL is transactional; if a migration fails the harness issues `ROLLBACK`, then final cleanup drops only the known fixture/migration objects. No database is dropped.

## Coverage and limits

The suite uses independent pool connections for same-invoice races, checks that a request row is committed before the provider test double runs, and races receipt allocation against initiation while both operations wait on a held customer-row lock. It exercises same-key replay without a second payment/event and with payload conflict, active-index states, ambiguous-outcome retention, terminal rejection release, tenant-scoped keys/composite event FK, event immutability, reconciliation audit idempotency-key and successful-checkout uniqueness, concurrent reconciliation with one resulting receipt, ordinary receipt verification/allocation/reversal replays, retention of a successful reservation after reversal, and rollback of reservation plus event when an injected trigger fails. These scenarios are prepared integration tests; they prove PostgreSQL behavior only after the opt-in suite has actually run against the guarded disposable PostgreSQL target. The tests have not been run as part of the static audit.

The audit table checks test raw database constraints and immutability; they do not execute the reconciliation service twice or simulate authenticated callback delivery. The event table intentionally has no SQL uniqueness rule for identical event payloads: duplicate-transition prevention depends on application transaction/state-transition logic. Duplicate callbacks, callback authentication, repeated reconciliation idempotency at the service boundary, and exactly-once journal/receipt posting remain unverified by this harness. Provider behavior is always a local injected function, not Daraja.

The account/customer/invoice/payment fixtures are synthetic. The suite cannot verify authoritative deployed schema, production migration history/permissions, Daraja response semantics, callback authenticity, real network timeouts, or refund/reversal policy. Its simulated nonzero initiation response exercises the application's rejection branch; it does not establish provider guarantees. Existing accounting and invoice PostgreSQL suites remain separate suites with their own fixed targets and guards.
