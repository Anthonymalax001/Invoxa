# M-Pesa STK Push verification

## Trust boundary and lifecycle

STK Push initiation is asynchronous. Daraja's initial acknowledgement and the public callback URL do not, by themselves, authorize accounting updates. The callback handler validates the documented envelope and required request identifiers, then acknowledges a well-formed delivery without changing the legacy payment row, invoice status, receipt ledger, or journal. Malformed payloads receive HTTP 400. No raw callback body is logged or stored.

The callback contract published in the [Safaricom Daraja M-Pesa Express documentation](https://developer.safaricom.co.ke/apis/MpesaExpressSimulate) describes `MerchantRequestID`, `CheckoutRequestID`, and `ResultCode`, with optional transaction metadata on successful callbacks. The repository and published material reviewed here do not establish a callback signature, shared secret, or another callback authentication procedure. The application therefore treats callbacks as untrusted notifications, not proof of funds.

An administrator with `accounting:manage-receipts` can use `POST /api/payments/:paymentId/mpesa/reconcile` to make a server-to-server STK status query for the checkout ID already saved on a tenant-owned pending request. The endpoint requires an `Idempotency-Key` and an explicitly selected provider transaction date. It rechecks the request and posted invoice snapshot under a row lock after the provider response. A result creates a customer receipt only when Daraja returns an accepted query response, the returned checkout identifier exactly matches, and a final `ResultCode` is zero. Missing, mismatched, or non-success results do not create receipts. A later non-success result after a previously verified success is retained as a conflict event; it does not undo or edit the receipt.

The Safaricom-owned [M-Pesa PHP SDK](https://github.com/safaricom/mpesa-php-sdk/blob/master/src/Mpesa.php) exposes the STK Push Query endpoint and its `BusinessShortCode`, `Password`, `Timestamp`, and `CheckoutRequestID` request fields. Its public method returns the provider response without documenting the response schema. The implementation therefore fails closed unless the response includes `ResponseCode`, the same `CheckoutRequestID`, and `ResultCode`. Confirm that response shape against the Daraja app and environment before enabling production traffic; any other response is treated as inconclusive or query failure.

## Receipt and accounting controls

A successful provider query creates an **unverified pending receipt** through the existing `customerReceipts` service in the same database transaction as its reconciliation audit event. The receipt is keyed idempotently from the checkout identifier and includes only minimal evidence metadata: query source and checkout ID. It does not store provider payloads, access tokens, credentials, callback metadata, or phone numbers.

The ordinary receipt verification workflow still requires an administrator to review external evidence, select a tenant-owned cash/bank account and an open accounting period, and confirm posting. Existing receipt allocation then applies the receipt to the matching customer invoice; only a fully allocated invoice is marked paid. The reconciler does not bypass these steps, post a journal, or edit a posted journal. A successful provider result dated in a closed period is retained in the M-Pesa audit as blocked and creates no receipt. Reconciliation will not change that provider transaction date; only the separately approved period correction/reopening process can make the same date eligible.

The legacy `payments` table has no repository-owned DDL and its status domain/constraints are unknown. For that reason the implementation never writes a success/failure value to `payments.status` or a provider receipt number into an assumed legacy column. Existing STK request rows remain `pending`; the append-only reconciliation audit and linked receipt represent the verified result. The UI exposes this distinction. A later schema recovery is required before migrating legacy payment status safely.

The checkout request amount, invoice total, and immutable issued snapshot total must agree exactly in KES. STK initiation only accepts an issued invoice whose full original balance remains outstanding; it rejects a partially allocated invoice instead of prompting for the full original total. It also rejects fractional-KES totals instead of rounding them and applies Safaricom's published KES 250,000 per-transaction ceiling. Partial-balance STK prompts remain unsupported; use the customer receipt workflow. The provider query does not supply a transaction date in the response contract reviewed here; an administrator must enter the date checked against the provider statement. If that date is in a closed accounting period, existing receipt controls reject creation. Do not change the date to an open period to work around that rejection; use the separately approved period correction process.

## Audit and schema

`mpesa_payment_reconciliation_audit` records tenant, opaque legacy payment key (stored as text because the legacy payment ID type is unverified), checkout ID, chosen payment date, provider result code/outcome, linked receipt, idempotency hash/key, actor and timestamp. Its rows are protected by an immutability trigger and a tenant-scoped unique key prevents a checkout from producing more than one verified-success receipt. The API history endpoint is tenant-scoped and returns at most the latest 100 events.

Apply `migrations/20261030_003_mpesa_reconciliation_audit.sql` only after the authoritative deployed schema is reviewed. It preflights the legacy `payments` columns it needs, intentionally creates no FK to that table, and depends on `tenants`, `customer_receipts`, `uuid_generate_v4()`, and the tenant UUID contract already required by the accounting migrations. This migration was not executed in this task.

`migrations/20261031_002_mpesa_stk_initiation_idempotency.sql` creates the request state and append-only request event tables. `migrations/20261031_003_mpesa_stk_invoice_reservations.sql` extends the state domain, adds event details and creates unique partial indexes for one active reservation per tenant invoice and one request per linked payment. Neither migration was executed. Migration 003 requires 002 to have been applied and preflights duplicate active invoice requests, duplicate payment links, existing status values and index-name conflicts; it aborts for manual review if any are found. Review both migrations against authoritative deployed DDL, UUID support, tenant key and migration-runner behavior before applying. Legacy `payments` rows without a matching request are not backfilled because their status semantics are unknown; reconcile and review those separately before rollout.

STK initiation, external-reference recovery and administrative resolution take a tenant/invoice PostgreSQL advisory lock first. Mutating receipt and reconciliation transactions then use the customer row as their serialization lock. They lock any invoice rows in ascending ID order, then reservation/request rows before the receipt row; reconciliation locks customer, invoice, initiation request, payment and receipt in that order. Allocation retries that find an existing idempotency batch return read-only before reservation checks. This shared customer lock prevents receipt operations from interleaving while a request/reconciliation holds invoice and request locks. The unique partial index is the database backstop for active invoice requests. Reservations require migration 003 and STK initiation fails closed when its unique index is absent.

All active states reserve the invoice: `reserved`, `outcome_unknown`, `provider_accepted`, `reference_recovered`, `payment_recorded` and `provider_succeeded`. The request is written before Daraja is called. Timeouts, missing/malformed identifiers and uncertain response persistence stay reserved and cannot automatically issue another prompt. Only a structured nonzero initiation `ResponseCode` without a checkout ID is recorded as a definite rejection; missing codes, timeouts, server errors and responses containing a checkout ID remain ambiguous. Daraja's published Express material documents a successful service acknowledgement as accepted for processing and a nonzero callback result as an error/failure; confirm the exact initial-response behavior with the Daraja app/environment before production use. The callback remains unauthenticated here and never changes this state. [Safaricom Daraja M-Pesa Express documentation](https://developer.safaricom.co.ke/apis/MpesaExpressSimulate)

A successful status query moves the reservation to `provider_succeeded` and creates the same unverified receipt used by the existing receipt workflow. The reservation remains active after provider success, including while the receipt is verified, allocated or reversed. Only the receipt linked to that exact successful checkout can be verified/allocated to its reserved invoice. Manual receipt creation/verification and other payment-channel allocations/reversals are held while a customer/invoice reservation could overlap; the reservation does not expire on receipt reversal. The existing M-Pesa receipt still needs ordinary evidence review, verification, accounting period/account selection and allocation. Neither initiation nor reconciliation posts accounting directly.

`provider_non_success`, query failure and inconclusive query results do not release a reservation automatically. The reviewed repository contract does not establish the STK Query result semantics needed to infer that no collection or active prompt remains. An authorized administrator can use `POST /api/payments/stk-request/resolve` with the original `Idempotency-Key`, `{ "confirm_no_collection": true, "confirm_no_outstanding_prompt": true, "resolution": "not_accepted|failed|cancelled", "evidence_reference": "...", "reason": "..." }` after reviewing provider records. This appends an immutable actor/time/event record with both confirmations, the supplied evidence reference and reason, retains any captured checkout ID, clears the phone, and closes the reservation as `resolved_no_collection`. This is an administrator assertion, not a synthesized provider response. The endpoint cannot release a `provider_succeeded` request. Same-key initiation replay remains idempotent; a released request requires a new key to start a later prompt.

An `outcome_unknown` request is never promoted automatically, even when an identifier appeared in an error response. An authorized administrator can use `/stk-request/recover` after locating the real checkout identifier in an external Daraja record, providing that identifier, the original phone number, an evidence reference and a reason. Recovery records an immutable `reference_recovered` event, creates only a pending legacy payment row, and enables the existing authenticated server-to-server status query; it does not invent a provider response or claim payment success. The phone is checked against the original request hash. If the provider record confirms no checkout/collection, use the audited `/stk-request/resolve` route. A process crash that leaves `reserved` is also resolvable only after the advisory lock has cleared and an administrator has verified no collection or active prompt in provider records. No cleanup job automatically releases old reservations.

## Provider and deployment requirements

- Configure the Daraja consumer key/secret, business shortcode, passkey, and callback URL through the existing secret/environment mechanism. Values were not read during this work.
- The current M-Pesa module is hard-coded to Safaricom's **sandbox** API host. Production host selection and live Daraja account/shortcode setup are not implemented or verified here.
- Configure the callback URL in the Daraja app to the public HTTPS `/api/payments/callback` route. Network reachability is provider-side configuration and was not checked.
- STK Query uses the OAuth credentials and shortcode/passkey already used by STK Push. Provider API calls were not made in this task.
- No M-Pesa request is considered received merely because the frontend was told the prompt was submitted. The user must use reconciliation and then the existing receipt verification/allocation controls.

Unit tests use mocked provider/database behavior. They do not prove PostgreSQL constraint, lock, trigger, migration, or production-schema behavior.
